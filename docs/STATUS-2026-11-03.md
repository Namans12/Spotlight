# Release Pulse: repository status, backup and what is still open

Written 2026-11-03 on branch `feat/release-pulse`. This is the single place to start.
Detail lives in the documents linked at the bottom.

## 1. What this is

**Release Pulse** is an agent built on top of the Spotlight OTT release radar for the Qloo
Agentic Hackathon. For a café or D2C food brand in a launch city it ranks upcoming
releases by local audience affinity (Qloo), shows an evidence-backed brief (audience skew,
heatmap, venues, themes, brands, artists, filming-location hook), writes a cited campaign
with Groq, and answers questions in a chat that only uses tool evidence. A thin consumer
slice adds a "Filmed in & set in" panel and a "Plan the night" card on the title page.

It runs as a separate Node service (`services/pulse/`) plus new pages in the existing
React app (`/pulse`, `/pulse/:city/:mediaType/:tmdbId`).

## 5. Product state, honestly

**Verified live (real Qloo, real Groq, real Indian releases):** IMDb-to-Qloo resolution;
heatmaps with coordinates; real cafés; food-family themes; food and drink brands; artists;
demographics for established titles; grounded campaign generation; chat tool calling;
rate-limit pacing under Groq's free tier; HTTP validation, CORS and guards; restart and
disconnect handling in controlled local tests.

**Not established (from `docs/submission/evaluation-results.md`):**
- A repeatable business advantage over the same model without Qloo was **not**
  demonstrated: plan choices matched 34 of 45 in the main run, and no customer study exists.
- City boards for current releases ranked **zero** titles in Delhi and Mumbai (Qloo's
  location-conditioned answers were too thin for new and obscure titles); the board falls back to
  an explicit date order.
- A natural-language request for an established title ("Friends") failed to reach existing
  evidence; only the explicit TMDB id worked.
- Never run: the Docker image on Linux/Node 22 (Docker is absent locally), a hosted
  deployment, signed-in flows, OMDb enrichment, mobile review.

The evaluation documents recommend **keeping public deployment on hold** until those gates
are addressed. This status page does not override that.

## 6. Merging: read this first

Merging `feat/release-pulse` into `main` is not a neutral step:

- The project README says every push to `main` auto-deploys the production Spotlight site on
  Vercel, so a merge would ship the `/pulse` pages and sidebar entry to the live app. Without
  `VITE_PULSE_URL` set they show a "not configured" state, but they are visible.
- The merge also changes two scheduled GitHub Actions workflows (`ott-radar.yml`,
  `ott-radar-nightly.yml`). Both new steps are `continue-on-error`, only run when their
  secret or variable is configured (warm) or when the Pulse tables exist (location sync),
  and never touch existing steps, but they run against production.
- The Pulse database tables arrive as `migrations/0016_release_pulse.sql`, applied by hand like
  every other migration. Nothing runs it automatically.

The pull request is a **draft** for that reason. Marking it ready and merging is a
deliberate step for you.

## 8. Open work, if you continue

In rough order (each is described in the linked documents):

1. Fix catalogue discovery for natural-language requests about established titles.
2. Implement the stronger hypothesis from the evaluation: established-title local research with
   confirmed outlet constraints, rather than ranking brand-new releases.
3. Reserve board slots for theatrical releases; show no-signal titles in the collapsed strip.
4. Frontend cleanup list (chat tool-line states, polling back-off on 429, focus handling,
   buffer cap, touch targets).
5. Run the container image on real Linux/Node 22 and deploy the service (needs your hosting,
   database and Vercel accounts; the Render blueprint is `render.yaml`, steps in
   `docs/submission/deploy.md`). Decide the Groq tier first: the free tier is 8,000 tokens
   a minute and 1,000 requests a day.
6. Final whole-branch review, then merge deliberately.
